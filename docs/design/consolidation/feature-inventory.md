# Workspace Factory feature inventory and CLI/plugin boundary

**Decision.** Put the operational boundary at the plugin server. Humans use `/factory`, with the steer pill for context-sensitive actions and one Factory panel for review and inspection. Steers and workers need a small plugin-backed machine interface for the commands their instructions actually give them. Reuse the existing Paseo workspace on enrollment, attach one coordinator, and add further live holders on demand. Keep Factory authority, identity, cache/quota policy and recoverable delivery on the server.

Evidence is from this checkout and installed Paseo **0.17.4**. “Caller” means a traced in-repo caller or an explicitly documented human/agent workflow. It does not imply observed usage or absence of external scripts. `H` below is `plugin/server/handlers.ts`, `R` is `plugin/shared/factory.ts`, `S` is `src/cli.mjs`, `A` is `plugin/shared/factory-args.ts`, `U` is `plugin/client/factory-submit.ts`, and `P` is `plugin/client/factory-panel.tsx`. `D` means the installed daemon's `/opt/paseo/releases/0.17.4/lib/node_modules/@getpaseo/cli/node_modules/@getpaseo/server/dist/server/server`; `SDK` means `plugin/node_modules/@getpaseo/client/dist`. All recommendations use **1** fully replaceable by Paseo, **2** substantially simplifiable via Paseo, **3** necessary thin adapter, **4** indispensable Factory decision logic, **5** historical, **6** not yet assessable.

## Configuration and settings inventory

The CLI loads a file before every operational command (`src/cli.mjs:310–314`). Plugin handlers overlay settings onto that file even when settings defaults exist, with a second “no file” path that synthesizes a base and requires both host fields (`plugin/server/config.ts:46–110`, `plugin/shared/settings-validate.ts:202,333`). This is two effective policies today. The 2026-11-25 decision ignores the JSON file entirely and migrates the persisted **plugin** settings, including v1/v2 documents (`TODO.md:16–17`, `docs/design/slots-live-design.md:147–194`). Old file-only values should have a clear setup message where needed. Local/workspace-only enrollment should not be gated on GitHub setup fields.

## Provisioning, scope semantics and confirmation

- **Existing-workspace enrollment (4).** Native listings and creation provide concrete workspace IDs, but do not decide scope ownership. Use one exact open workspace, explicitly adopt a suitable native agent or create one, verify its actual provider/model, workspace, parent-free state and durable identity, then activate with a locked epoch write. Preserve existing checkpoint, ownership and continuations. Avoid requiring GitHub fork scans for routine status, switch, and local enrollment. Lists can use the native project/workspace relationship. GitHub visibility still matters for sensitive workers.
- **Fork, clone and upstream setup (2).** This is valuable as a separate onboarding convenience if users still rely on it. `src/github.mjs:77–135` verifies network identity, handles renamed forks and rejects ambiguous/mismatched forks. That policy belongs with the optional GitHub operation. Native `paseo clone` delegates to `cloneGithubProject` (`…/@getpaseo/cli/dist/commands/clone.js:29–35`) and registration endpoints create/list workspace/project. These transport operations do not implement the fork-ownership and existing-checkout policy. Start by enrolling a workspace the human already selected. Do not autoclone/fork when only handing off.
- **Plan after initial enrollment (2).** Keep a read-only repair/status view and an explicit repair path when an active holder is missing or ambiguous. Stop daily plan/retitle/top-up/expected-profile reconciliation. Use explicit steer add/adopt and dedicated holder classification. Product decisions already require exactly one coordinator in plan/apply, standby demand-based, sparse live slots and actual agent tuple (`docs/design/slots-live-design.md:98–116,189–194`). Detect explicit imported duplicate candidates before activating.
- **One scope identity and a small graph (4).** Keep canonical scope record/home workspace ID, current holder ID, epoch and generation, with a human display alias. Existing `src/scope.mjs:135–262` handles GitHub, dir, native-workspace/worktree and one hub plus paths, `local/<folder>`, `worktree:` and repo aliases; preserve ambiguous-address refusal. Worktree parent links carry GitHub visibility and are distinct from a logical domain. Domain is a pointer, hub is a special scope; keep assignment/reporting/escalation with the topology required by the live-slots decisions. Drop hub-specific provisioning syntax and domain-first mixed-plan batching if enrollment is singular, but keep cycle-domain and ambiguity checks at relation updates. Paseo Hub is integration automation, not the same logical coordinator. [Paseo Hub concepts](https://paseo.sh/docs/hub/concepts)
- **Adoption versus relocation (4/6).** Adopt native existing agent identity only after validating ownership/continuation and explicit detach when necessary. Relocation is cross-workspace authority transfer, not a path rename. Existing code initializes/adopts the destination as main, creates destination steers, sets source `movedTo`, then archives the source **after releasing the first lock** (`src/relocate.mjs:197–265`). An interruption here can leave both discoverable, and a retry must reconcile which holder is authorized. If relocation stays, stage destination inactive, fence source, transfer with a durable transaction/activation receipt, explicitly rebind workers, and verify one active authority. Dropping this feature removes a meaningful failure state; direct evidence of routine demand would justify repairing it.
- **Workspace cleanup (2).** Native archive is the actuator. Daemon `D/workspace-archive-service.js:34–78,265–318,362–395` archives agents/terminals, deletes backing worktree only if owned and unreferenced by another active workspace. It does not promise the Factory loss inventory/approval, especially untracked/ignored work or archived-scope semantics. Archive accepted worker agents directly; never equate their lifecycle with workspace removal. Existing cleanup also has distinct project deletions, ignored-loss inventory and report-only candidates, documented at `docs/configuration.md:259–266`; archive actions should be explicit. Missing-path and test leftovers may merit a narrow read-only inventory.
- **Legacy data (5 once migrated).** `src/paseo.mjs:22–57` normalizes `ari.wsf`/ `ari.wsf.*`, `src/planner.mjs:324–353,467–516,581–601` schedules migration and standalone/title candidate checks, `src/apply.mjs:699–749` rewrites metadata/labels. Agent label cleanup currently keeps old keys because the CLI patch is additive. Preserve read fallback until inventory proves migration, then narrow it to one ingestion path and archive `labels` and implicit title-only adoption. Preserve older checkpoint parsing if persisted answers still need it (`docs/steer-instructions.md:146`), and normalize old delivery records before closing retries (`plugin/server/steer-delivery.ts:108,195–238`). Keep ZeroSub continuation as current live compatibility. Reject stale plan hashes, including previous `ari-wsf:` idempotency-key namespace plans (`docs/configuration.md:257`).
- **Confirmation and retries (4).** There are two useful guarantee levels. Durable plan/apply authorizes exact compound operations and reconciles attempts from receipts even after restart (`src/apply.mjs:65–131,162–305`). Simple previews are fingerprints re-derived server-side for switch, checkpoint, fresh, assign, relocate, labels and steer add (`plugin/shared/preview.ts`, `H:850–921,987–1049,1287–1327,1461–1509`). The CLI often reruns with `--apply` using newly resolved inputs, a weaker tie to the previous preview, plus a few separate epoch options. Unify the confirmation envelope and renderers for active-holder/target-generation changes, explicit exhausted-account selection, destructive context/history actions, adoption and provisioning. For a read or idempotent self-resume on an unchanged target, a direct intent can be sufficient. A confirmation fingerprint must bind all decision inputs, then revalidate/fence under the same scope lock; a client-side re-preview or native metadata write alone does not establish that guarantee. Persist pending delivery independently of the UI and reuse its stable client message ID on retry.
