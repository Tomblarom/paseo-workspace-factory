# Workspace Factory internal architecture consolidation

Read-only review of Factory commit `a7c5cb6` and installed Paseo 0.17.4. Factory references are relative to the repository. **SDK** means `plugin/node_modules/@getpaseo/client/dist/`. **Daemon** means `/opt/paseo/releases/0.17.4/lib/node_modules/@getpaseo/cli/node_modules/@getpaseo/server/dist/server/server/`. Parsed source only. No live actions, provider calls or runtime fault injection. At that commit `src/*.mjs` was canonical and the plugin carried a generated copy of it (removed since; the core now lives in `plugin/` directly). The generated copy is excluded from the inventory and estimates.

Classifications: **1** fully replaceable by Paseo, **2** substantially simplifiable via Paseo, **3** necessary thin adapter, **4** indispensable Factory policy, **5** historical removal candidate, **6** not yet assessable. Estimates are net implementation ranges to validate in a diff, with overlap between candidates. Tests and temporary compatibility code are excluded from the estimates.

## Conclusions

- Apply the two existing P0 items together where ownership can change before delivery. A switch currently commits its epoch before it queues a message. A crash in that interval leaves a new coordinator and no recoverable delivery record. Warm delivery has a second gap between provider admission and recording the worker acknowledgment.
- Paseo already owns durable message and creation receipts. A message key is safe to reconcile only with the same recipient, payload and dispatch options. An unknown pending receipt is a real outcome. A fresh key would bypass protection and could buy another model turn.
- Keep provider-specific effect evidence, account selection, worker ownership, handoff semantics and checkpoint freshness. Merge action reservation and message acknowledgment, and consolidate the narrowly equivalent helpers. Agent, workspace, account and scope identity have different purposes.
- An independent defect currently prevents production replacement creation on the stated installed version. The receipt lookup only admits 0.16.2. Do not just remove the version check or add 0.17.4 to the list without equivalent evidence.

## Delivery, recovery and retry paths

Counting convention: a **delivery path** owns a distinct effect/acknowledgment sequence for the primary brief or wake. Alternate packet builders, direct and queued caller aliases sharing that sequence, and explicit optional notices are not counted twice. **Ten paths** using this convention. The same-tab Fresh code is counted once for active/inactive/worker, and replacement send is split only where commit/recovery is materially different.

| # | Primary delivery path | Recovery difference |
|---|---|---|
| 1 | Warm `deliverSteer` (switch with plugin, manual resume, worker wake, takeover request, staged send when warm) sends untracked with optional behavior (`plugin/server/steer-delivery.ts:419–429`). | Wake callers ack separately (`plugin/server/supervise.ts:640–679,1406–1428`); ready state and message identity absent. ## Minimal P0 design grounded in the inventory

### One action record per operation

Keep the per-agent workspace metadata and existing critical section. Introduce `wsf.agents[id].action` as a single live operation for that target, with a bounded last result or receipt reference for observers such as switch wait. Scope actions that change the target (switch, replacement) reserve the record alongside the verified transition or before invoking create, as described below. No general workflow engine. The dispatcher needs the existing effect executors plus a small set of guarded transitions.

1. **Reserve.** Under the scope lock, validate expected epoch and exact selected holder/eligible target. Persist `id, kind, epoch, at`, the evidence needed for the next effect, and any worker batch/revision. Keep route decision (warm/send, clear, compact, rewind, replacement) in the callers. Use the current packet builder when preparing a send and freeze the exact recipient, payload and send options before its first dispatch. Each irreversible step has its own stable key, e.g. clear and brief use different message IDs derived from the same action ID. Idle cleanup has no brief unless seed was independently selected. When the user explicitly chooses stage, a recorded manual-send intent has no effect until Initialize; dismiss verifies its action ID.
2. **Dispatch one recorded step.** Persist step and attempted marker before releasing to Paseo. Mark as never attempted again only for locally proven pre-dispatch refusal. Revalidate holder/epoch, action ID, live session, permissions/activity and batch immediately before the effect. Keep lock sections short; avoid holding them while a turn runs or over nested calls. Multiple processes use a lock-protected claim for first dispatch, not just a process-local Set. Avoid timing-based takeover. Reserve same-tab Fresh, sweep rewind and settings rewind before touching the context. A pending reservation for that agent excludes competing renewal. When the action belongs to a different target from the coordinator, guard both the authorizing scope and target eligibility; persist source and target fences for cross-scope takeover.
3. **Observe.** Before any repeat, interpret native observations for the attempted step. Clear needs correlated command or exact provider transition, prior/new non-empty unequal sessions, and current session still matching the resulting clear. Compact needs matched turn and a completed native marker or provider-specific trustworthy evidence. Rewind success is native acknowledged persistence; use prior anchor/session, timeline replacement and post-state to reconcile after transport loss only when they uniquely prove the requested transition. If no reliable correlation is available, keep `uncertain`; do not infer no effect from an error. For send, exact replay of the immutable key/request is native receipt reconciliation on 0.17.4. The server reuses completed, performs a new dispatch when positively no receipt is present, and refuses pending with `agent_request_outcome_unknown`. Never mint a new ID or change payload for an attempted send. Do not treat a visible submitted prompt row or source-agent queue acceptance as completed admission. Creation uses the authorized pinned request and receipt/observed identity, including same workspace, exact parent/labels and expected account.
4. **Advance and finish.** Minimal progress can be represented as next expected step plus `attemptedAt?`, `observed?` and an explicit blocked/uncertain explanation. No need to persist independent `pendingAction` and delivery phases with overlapping meanings. After renewal proof, build a brief from fresh facts if needed, recheck checkpoint revision and last turn before pinning. Freeze once attempted, so later checkpoint changes cannot alter native fingerprint. If target authority moved, stop sending and expose the record for reconciliation. Record confirmed admission before clearing matching worker events. Acknowledgment uses original event identity (`workerId,state,queuedAt`, source epoch), and may be safely retried after a crash without another send. Clear `needsResume` only if its captured revision still matches. Keep the last observed cleanup/rewind timing, anchor and bounded old sessions for cache behavior/history; those are reusable evidence, distinct from a pending dispatch. A completed manual stage dismiss acts only on the matching unattempted record.
5. **Bridge authority transitions.** Switch with send writes new scope state and target's handoff reservation in the same native metadata patch. Store the checkpoint revision and enough packet inputs or the packet to recover without a model call. Self-takeover still progresses without a self-message. Fresh reserves on the old holder before create, pins the creation key, then atomically records verified replacement identity and deliverable continuation when transferring agent state/register/active epoch. If the daemon returns no authoritative outcome, surface it and keep the existing worker/old history. During recovery reconstruct at most an unattempted packet; reuse a pinned packet exactly after any attempt. This removes the current worker start/resume packet fingerprint mismatch. Quota is checked before actions that could start a model turn, and again after a defer; account pin, privacy, pending ZeroSub move and reset windows stay intact.
6. **Use one reconcile entry.** Hook, inline completion, post-boot/supervision timer, CLI/RPC resume and wait call or observe the same reconcile code. Hook provides correlated evidence; poller handles interrupted bookkeeping and new eligibility. Retry transport observations or a native exact request when contract permits, never an unverified clear/compact/rewind. Explicit blocked vs uncertain is projected consistently into CLI, pill and readiness selectors. Read legacy records through one decoder. Upgrade only when evidence is adequate; map old renewing records with unknown outcomes to attention, preserve stable sent keys and queued worker events. Remove legacy writer paths after a migration pass and fixtures, while keeping prefix compatibility until supported data inventory is known.

**P0 sequencing.** First reserve and reconcile warm/cold steer delivery, switch and staged intents, because they share the same sender and worker acknowledgments. Then move clear/compact/sweep and both Fresh routes onto that record. Bring settings and assignment/report in only where they share the exact send acknowledgment; keep distinct intermediate effects and authorization. Administrative plan/relocate can reuse the creation evidence adapter and pinned-delivery stage without making plan authorization a per-agent object. Preserve existing worker state transitions and warm baseline as inputs.

### One shared scope guard

A stale CLI process of the same agent after A → B → A is an accepted limit: Paseo does not bind the process to a turn or epoch, and the agent is again the legitimate holder.

Use a core guard called in the existing locked reread, with an expected scope ID/workspace, integer epoch, and **exact active agent ID** (plus slot where appropriate). Resolve the current holder from the fresh observation using the same continuation/supersession/ambiguity semantics as status. Reject missing/archived state, no unique current active holder, stale epoch, inactive/advisor/superseded caller, invalid workspace or coordinator parent. Verify the lock inode before write. Use an explicit authority at entry points:

- Scope-changing agent requests require the active caller in the expected epoch. `checkpoint --from-agent` must resolve a unique ID and select that holder under the guard, and reuse the same core writer in CLI and RPC. The manual human path may intentionally enter fields with an explicit preview-bound scope. A host or user confirmation is part of this operation's authority, not evidence of an agent identity.
- Self-takeover and human switch have named policies. Both use the same fresh epoch/current-holder check; target self-takeover checks target identity and source inactivity while preserving self/no-send. Hub/domain assignment validates the requester/source relation and destination epoch; agent-targeted inactive Fresh/settings/resume can maintain its tab and must never overwrite the active scope checkpoint. A worker recovery guard verifies existing membership and active coordinator generation without claiming that the worker itself is a steer.
- Hooks use trusted payload identity and compare the observed epoch and current holder for scope writes. Agent-specific bookkeeping still checks relevant turn/action generation without demanding that an inactive agent own the scope. Host-global/config and first-provision actions retain their own revision/authorization. Plan cleanup or archival touching a live scope goes through the same scope check where an ownership state exists.
- For legacy `activeSteer` slot-only records, resolve once from verified, unique membership. Do not infer new ownership from a candidate tab appearing during Fresh. Consider storing the exact active agent ID next to the existing slot **only** if current-holder resolution cannot be made stable across reservation/registration and ZeroSub continuation. In that event change it atomically with the existing state and migrate conservative ambiguous cases; avoid a second independently updated owner record.
- The installed plugin handler context supplies a Paseo API and request signal, with no authenticated originating Factory agent ID in this contract (SDK `@getpaseo/plugin/dist/server/contracts.d.ts:9`; current RPC forwarding `plugin/index.server.ts:173–178,198–219`). A raw RPC agent ID is target data. CLI `PASEO_AGENT_ID` is cooperative self-identification on this single host, not a trust boundary. Never substitute target ID for an authenticated source. Keep human/operator-confirmed RPCs and automatic plugin hooks explicit; stronger cross-host/caller authentication or atomic send-if-idle requires an upstream capability. The guard is an ownership and epoch fence for cooperating Factory paths.
