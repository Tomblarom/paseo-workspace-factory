# Steer menu and cache-aware settings

## Composer pill

Show one persistent Factory pill on every registered steer tab with a composer, including standbys, advisors and visible former holders. The Factory attention pill for workers stays as it is. A standby can inspect its own state, while actions that change scope ownership follow the existing caller and role checks. History-only tabs can open the Factory panel when Paseo does not render a composer.

The collapsed label is the slot and one state, such as `A · Warm`, `B · Limited`, or `C · Cold`. Expand it to see `Steer A · Active`, the provider, model, thinking and speed, context size and estimated cache time, and one row per account-wide quota window, such as `5h 54% used · resets in 1h 12m` or `7d 48% used · resets in 2d`. Show the account label or fallback pool, percent **used**, and countdown to each known reset. A model-specific window that applies to this steer gets a separate labelled row. An API account with no windows shows `No quota data`. An expired sample shows `Awaiting quota update`. The tooltip and accessible title include the slot, role and state. The header can include secondary facts such as `Large context` while the face says `Running`.

Use ZeroSub's stable pill registration and live popover pattern. Its `pills.ts` and `pills.test.ts` show a compact usage face and in-place updates, `account-menu.tsx` wraps reset details, and `account-pill-button.tsx` and its test check native-looking theme colors and show the limits of custom composer placement. Use Paseo's `addComposerPill` with a stable popover component. Patch the face only when it changes. Use a local menu page with Back for handoff targets, and keep an open preview mounted across quota ticks. Use the host popover on desktop and verify its compact layout and overflow with the ZeroSub pill visible. ZeroSub continues to own `Follow default`, `Continue on …` and `Manage accounts…`. [Paseo composer pills](https://paseo.sh/docs/plugins/reference#composer-pills)

Replace the steer portion of `index.client.tsx`'s conditional attention feed with the permanent pill. Reuse the cold panel's continuation actions and saved-history entry where the chosen route is valid. Keep `factory-popover` and the Factory panel as status and preview destinations. Show `/factory` results from the originating steer inside its own menu or panel. The transient result pill currently has one mutable registration for all agents and a 60-second expiry. A per-agent result keyed by host and agent avoids replacing an open menu when a different steer runs a command. ## Status calculation

Use labelled steer discovery and its continuation/supersession rules. Combine live Paseo agent and composer state, Factory turn/checkpoint metadata (`wsf.agents`), pending operations and account or pool quota into one small host-scoped projection. Subscribe once per host or scope and register pills for all known steer tabs, including older agent pages. Keep the last verified membership through a transient disconnect and render `Unknown` until refreshed. On authoritative removal, remove that registration. Countdown ticks are local, with an update at the next state boundary. Reuse existing quota sampling and avoid timeline fetches, provider calls and per-agent polling for the face. [Cold context data and hooks](cold-context-resume.md#data-model) · [Cold feed](../../plugin/server/cold-sweep.ts) · [Live slots](slots-live-design.md)

**Context size.** Use the live agent's finite, nonnegative `usage.usedTokens`, then the last stored `contextTokens` for the same session/generation. Missing stays unknown. `Large` means `tokens >= effectiveMinContextTokens(profile, cleanup.minContextTokens)`. Default `balanced` and `comfort` use the configured floor (60,000 by default). `efficiency` uses the lower of that floor and 10,000. Keep the optional `usage.warnContextTokens` status warning separate from this routing floor. A `freshHint` valid for the current idle period affects the recommended action independently of size. [Cache profile code](../../plugin/shared/cache-profiles.ts) · [Existing status warning](../../src/steer.mjs) · [Fresh hint validity](../../plugin/server/factory/agent-state.ts)

**Cache age.** Resolve the live provider, model and confirmed billing route with this table. For the initial estimate use `now - lastTurnEndedAt` after a provider turn with a usable, matching session/config baseline. For Claude, prefer the most recent confirmed cache-writing or cache-reading request start once available. Anthropic measures its TTL from request start, so turn end can overestimate warmth. Preserve the start separately if adding it to the turn summary. Reopen, clear, rewind, confirmed account changes or a cache-affecting config delta invalidate the old baseline for this decision. A verified empty replacement or rewind awaiting its first brief is `Ready`. Mark every TTL-based state as estimated in the header and keep cache warmth and quota independent. [Factory cache spec](codex-research/spec-cache-profiles.md) · [Factory cache reference](cold-context-resume.md#cache-reference-and-cost-profiles) · [Claude cache lifetime](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#when-does-the-cache-lifetime-start) · [OpenAI retention](https://developers.openai.com/api/docs/guides/prompt-caching)

| Live route | Estimated TTL for the pill |
| --- | --- |
| Claude or known Claude model | 60 min for the Factory subscription baseline or a confirmed 1h path. Use 5 min on a known 5m path, including default Anthropic API caching. Use 5 min with `Billing path unconfirmed` when the route and its retention are unknown. |
| Codex/OpenAI GPT-5.6+ | 30 min. Match `groupForProviderModel`, including unversioned IDs from an identified Codex/OpenAI provider. The retention estimate applies to the Factory decision, including where the API can retain entries longer. |
| Codex/OpenAI GPT-5.5 and earlier | 10 min for the Factory legacy in-memory estimate. Use 30 min if extended retention is confirmed. |
| Other | 30 min as the existing cleanup heuristic. Show `Unknown` for cache state unless that provider's route and baseline are supported. |

`coolingMinutes = max(1, min(10, round(TTL / 6)))`. For valid age and matching baseline, warm is `[0, TTL - coolingMinutes)`, cooling is `[TTL - coolingMinutes, TTL)`, cold starts at `TTL`. This gives 50, 25, 8 and 4 minutes to the start of Cooling for TTLs of 60, 30, 10 and 5 minutes. The display is independent of when cleanup is eligible. Missing or future timestamps, a missing baseline, or an unmeasurable effective route yield unknown warmth. A known prefix break with retained history is treated as cold for the new configuration.

**Quota.** Prefer a supported `zerosub.state` version and a matching live route. For a move still pending, `pendingAccountId` is the current session and `accountId` is its destination. Keep both and `waiting` (`idle`, `turn`, `background`, `restart`) in the projection. Fall back to the effective **live** provider/model pool in the cached `paseo usage --json` sample when the account route or quota fields are unavailable. Prefer a confirmed live account limit to a pool estimate. Use the latest successful sample and show its timestamp. Mark percentage data stale after two source sampling intervals (Factory pool default 20 minutes at its 10-minute sampling interval), or as soon as a reported window resets without a fresh reading for that window. Preserve explicit future `limitedUntil` or snapshot `limitUntil` separately from ordinary `resetsAt`. [Current Factory quota normalization](../../src/zerosub.mjs) · [Pool normalization](../../src/quota.mjs) · [Quota sampling](../../plugin/server/quota.ts)

`Limited` follows fresh explicit limit status, a future `limitedUntil` / `limitUntil`, a current unrecovered `needsResume: limit`, or a relevant fresh window at the effective Factory exhaustion threshold (default 90%; warning 75%). For threshold-only evidence say `Factory quota threshold` in details. Consider whole-account windows for all steers and model-only windows only when they govern the selected model. A signed-out or disabled account makes its row unavailable with that reason. Display each blocking window's own reset. If one timer is needed, use the latest of all known blocking reset times and any explicit hold, with `Reset unknown` if any blocker has no time. Recheck at a reset. A past reset or newer usable evidence retires the limit inference from the failure for that route. The stored recovery flag still needs handling. The current quota RPC's flattened maximum and single reset are insufficient here. In particular a normal `resetsAt` is present on usable accounts and cannot by itself create a hold. [Quota rules](quota-independence.md#d-share-limited-quota-across-codex-and-claude) · [Current quota RPC](../../plugin/server/quota-rpc.ts)

### Face priority and primary action

For a connected host with resolved membership, take the first matching row. The header keeps the lower-priority facts, including `Large context` and `Waiting for reset`. Use the names below with the slot prefix. The icon may use a themed render component through `PluginButtonIcon`. The host owns label chrome. Semantic colors come from `theme.colors` and the text and icon carry the state as well.

| Label | Exact condition | Icon and theme color | Primary action |
| --- | --- | --- | --- |
| **Retired** | Scope is retired, the tab is its recorded replaced holder, or discovery marks it superseded by the unique current holder. | `Archive`, `foregroundMuted` | Open the current holder or successor scope. |
| **Running** | Live status `running`, or a current-generation open turn that has not ended and is not marked interrupted. | `Activity`, `accent` | View turn. Label a pending interaction `Review request` when permission is needed. |
| **Limited** | Limited by the quota rule above. | `Gauge`, `statusDanger` | Preview handoff to an eligible steer or show reset details if none is eligible. |
| **Waiting** | Live `initializing`, an unresolved Factory operation on this holder, a queued wake addressed to this holder (legacy worker wakes apply to the current active holder), or a verified pending ZeroSub move. | `Clock`, `foregroundMuted` | View the operation, queue reason or scheduled reset. For `waiting: restart`, show the required session action. |
| **Needs resume** | `needsResume` is `daemon-restart`, `failed`, or a recovered `limit`, or a current-generation `interrupted` record has no verified recovery. | `RotateCcw`, `statusWarning` | Preview recovery. Use a compact-brief refresh for a large cold or uncertain context. |
| **Ready** | Proven history-free current session, or a verified context reset with the first brief still to be staged and no active operation. | `CircleCheck`, `statusSuccess` | Focus composer, or preview and deliver the staged brief. |
| **Cold** | Valid age at or past TTL, `needsResume: cold` applies to the current session, or a known prefix break makes retained history risky. | `Snowflake`, `foregroundMuted` (warning color if large) | Preview refresh if large, size unknown or a fresh hint applies. Otherwise focus composer with a reuse estimate. |
| **Large** | At or above the context floor with warm, cooling or unknown cache age. Show the underlying warmth and any expiry in the header. | `Layers`, `statusWarning` | Preview refresh at a checkpoint boundary, or consider warm compaction mid-package when eligible. |
| **Cooling** | Valid cooling age within the TTL. | `Timer`, `statusWarning` | Continue now. Offer refresh when there is a valid fresh hint. |
| **Warm** | Valid warm age and no higher-priority condition. | `Flame`, `statusSuccess` | Focus composer. Surface a valid fresh hint in the header. |
| **Unknown** | No higher-priority rule and insufficient comparable evidence, including a disconnected host or ambiguous membership. | `CircleHelp`, `foregroundMuted` | Reload status or open Factory to resolve membership. |

Boot checks can set `daemon-restart` for a recorded open turn or a recent steer under `recentHours` (default 24). A failed-turn hook sets `limit` or `failed`. An interrupted or cancelled turn can have `interrupted` without `needsResume`. A closed agent alone stays eligible for a wake if Factory can verify its state. Use existing flag-clearing rules after verified recovery or a successful turn. The cold helper currently uses generic idle settings and can select direct continuation for a failed/limited small session. The menu should pass the resolved TTL and current quota/size evidence into shared routing, and honor verified reset and recovery results. [Boot and failure rules](../../plugin/shared/idle-cleanup.ts) · [Resume design](cold-context-resume.md#r--factory-resume-as-the-restart-path) · [Current continuation helper](../../plugin/shared/context-continuation.ts)

## Settings changes and efficiency lock

### What changes cache reuse

| Change | Claude | Codex / OpenAI |
| --- | --- | --- |
| Model | Cache is per model. An actual model change loses the previous model's cached prefix. [Claude cache diagnostics](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics) | The API identifies `model_changed` as a cache miss. Treat a different effective model as a new prefix. [OpenAI cache diagnostics](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics#fix-a-cache-miss) |
| Thinking / effort | Changing thinking mode or `budget_tokens` invalidates message caches, and can invalidate system/tools. Top-level `output_config.effort` can do the same. Explicit default is equivalent to omission. A supported per-message effort change can preserve the earlier prefix. Paseo's live setter requests a Claude query restart. [Claude caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#what-invalidates-the-cache) · [Paseo Claude adapter](https://github.com/getpaseo/paseo/blob/v0.16.2/packages/server/src/server/agent/providers/claude/agent.ts#L2868) | Changing request-level `reasoning.effort` can rewrite hidden instructions. Supported GPT-6+ API requests can append `configuration_update` with the original top-level effort unchanged. Paseo 0.16.2 updates the Codex thinking option for the next turn. Its plugin contract does not expose the append-only mechanism, so treat an effective effort change as at risk until measured on that route. [OpenAI caching](https://developers.openai.com/api/docs/guides/prompt-caching#change-reasoning-effort-without-rewriting-the-prefix) · [Paseo Codex adapter](https://github.com/getpaseo/paseo/blob/v0.16.2/packages/server/src/server/agent/providers/codex-app-server-agent.ts#L4902) |
| Fast / priority | An actual standard-to-fast or fast-to-standard speed change invalidates system and message caches. The tool prefix can still hit. Claude Code Fast also has different usage charges. Paseo uses the Claude `fast_mode` option. [Claude caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#what-invalidates-the-cache) · [Claude Code Fast](https://code.claude.com/docs/en/fast-mode) · [Paseo Claude options](https://github.com/getpaseo/paseo/blob/v0.16.2/packages/server/src/server/agent/providers/claude/agent.ts#L2889) | A different effective `service_tier` can miss, even though eligible cached input can also receive a discount within Fast. Compare resolved tier IDs, including aliases and fallback. Paseo uses `service_tier` for Codex. API evidence supports a conservative default. Verify the ChatGPT subscription route separately. [OpenAI cache diagnostics](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics#fix-a-cache-miss) · [OpenAI Fast](https://developers.openai.com/api/docs/guides/fast-mode) · [Paseo Codex options](https://github.com/getpaseo/paseo/blob/v0.16.2/packages/server/src/server/agent/providers/codex-app-server-agent.ts#L4911) |

Use normalized effective values when comparing settings. A no-op spends no turn. Account changes, instructions, tool definitions and provider-specific options can also change prefix reuse. Treat API documentation as evidence for the documented API. Confirm the effective provider and tier, cache-read input, new input and quota delta in controlled Claude Code and Codex subscription trials before enabling any cache-preserving shortcut.

### Apply the requested change

1. Read the live catalog and the composer's model, thinking and effective options. Show the selected tuple and candidate route before applying. Allow a direct change while idle on an empty or known small context if the catalog supports it and the efficiency lock does not apply. Show a cache-risk or premium-speed note on an effective change. Keep the persisted Factory slot profile and global default separate from the per-agent choice.
2. For a cache-risking change on a large context of any age, an uncertain history size, or a context covered by the efficiency lock, prefer **Continue in a new tab** as the next holder of the same slot. Create a parent-free replacement with the requested provider/model, thinking and speed already set. Start from the stored checkpoint and a bounded brief with task, tests, blockers, next step, relevant paths and unfinished workers. Preview any missing checkpoint and require a reviewed brief before proceeding. Keep the previous agent available in history and signal replacement through labels/metadata and UI. Use the existing no-notification switch option and replace `fresh`'s outgoing-agent message with a UI notice on the efficient path. Stage the brief for the first real request where possible. Otherwise send it once after the new holder is verified. [Fresh and switch implementation](../../src/steer.mjs) · [Quota design, dispatch and renew](quota-independence.md#c-warn-before-costly-turns-and-renew-by-opt-in)
3. Offer **Refresh this tab** for a supported same-provider rewind only after verifying a real user-message anchor, a settled turn with no pending permission or background work that would be lost, and history recovery where available. Capture the checkpoint and preview transcript loss first. Rewind conversation, confirm the short context, apply and verify the settings, then deliver or stage the brief. Existing `fresh` rewind delivers a brief itself, so add a stage-only path before using it here. If a rewind or config write fails, keep the brief and draft recoverable, report the last confirmed step, and let retry reconcile it. Never silently send the brief into the large prior session. Use the new-tab route for provider changes or unsupported rewind. [Same-tab refresh](cold-context-resume.md#same-tab-refresh-via-rewind)
4. Allow **Apply here** on risky large contexts only as an explicit, cost-labelled override in balanced or comfort mode. Verify final effective settings after any write, including model-induced resets of thinking or speed. Keep the transition recoverable if only part of the tuple applied. Never mutate a running steer from the menu. Resume or handoff uses the live quota and privacy checks on the selected destination.

### What Paseo 0.16.2 supports

The installed `@getpaseo/plugin` version is 0.16.2. In `dist/server/lifecycle.d.ts`, `PluginHookRequests` has waiting hooks for worktree/workspace creation and agent creation/open. `PluginHookEvents` has turn, permission and agent/workspace lifecycle notifications. `agent.turn.before` is a `void` notification fired at turn start. There is no config-change hook on either list and no veto at Send. Create/open hooks act at different lifecycle points. [Paseo hook table](https://paseo.sh/docs/plugins/hooks#hooks)

In `dist/client/contracts.d.ts` and `dist/client/buttons.d.ts`, `addComposerItem` adds a plugin component and `addComposerPill` can disable its own button. The installed `dist/client/composer.d.ts` exposes effective values and setters through `useComposer()` and reactive `useComposers({ agentId })`. It has no control-disable API. The app's native control in the v0.16.2 tag calls `setAgentModel`, `setAgentThinkingOption` and `setAgentOptions` directly. Observing the resulting model/thinking via the agent subscription and options via the composer is therefore after the write. There is no dedicated public plugin config-changed event. [Paseo composer items](https://paseo.sh/docs/plugins/reference#composer-items) · [Paseo native controls at v0.16.2](https://github.com/getpaseo/paseo/blob/v0.16.2/packages/app/src/composer/agent-controls/index.tsx#L1066-L1165)

`cache-profiles.ts` defines exactly `efficiency`, `balanced` (default) and `comfort`. For **Maximum efficiency** (`efficiency`), lock effective model, thinking and speed changes on a warm or cooling steer, including a `Large` face with warm or cooling underneath. Apply the same protection during a running turn, independent of the face. A verified cache-preserving variant can be exempted after live evidence. The Factory menu can enforce its own route policy today. For native settings, show `Use the Factory menu to keep context costs down` before edits when the pill is opened. While the tab is observed, retain the last normalized tuple and turn identity. If an external change arrives, show `Settings changed · cache at risk` once and keep it in the pill title and header with **Revert settings** and **Continue with fresh context…**. Only offer revert while idle and while the current tuple still equals the observed change. Revalidate and verify the restored tuple. A revert cannot promise a cache hit or refund a turn already started. A first snapshot or reconnect with no comparable baseline is `Unknown`, and a change from the Factory's confirmed route does not raise its own warning. Avoid automatic reverts and repeated toasts. Until the upstream feature is available, describe this native behavior as a warning. [Factory cost profiles](../../plugin/shared/cache-profiles.ts) · [Observable composer state](https://paseo.sh/docs/plugins/reference#reach-a-composer-by-reference)

**Minimal upstream proposal.** Add one per-agent config guard with a capability flag and an awaited `agent.config.before` decision at the daemon's common model/thinking/options mutation boundary. Supply the agent ref, source, current effective settings, proposed delta and config revision. Return allow or deny with user-facing text. Evaluate the guard before persisting or applying to the provider, and use the same policy for app, CLI and SDK writes. Let a plugin publish which fields are restricted and why to the host UI so the native Model, Thinking and Speed controls can disable with a tooltip and open the Factory menu. Release that restriction when the plugin stops, and recheck on the server for stale clients and races. Allow a scoped, single-use authorization for the exact confirmed Factory transition, including its revision. Keep draft creation and unrelated fields on their usual paths. A Send guard for arbitrary user prompts would be a separate feature.

## Additional ways to save quota

| Approach | Expected benefit | Feasibility |
| --- | --- | --- |
| Warn before a short prompt into a large cold context | Avoids replaying a large transcript for a small task. | Show the persistent warning today. In Factory-owned dispatch, a proposed threshold of ≤512 estimated input tokens with no attachment can offer fresh, side worker or explicit continue. Native Send-time decisions need an upstream guard. Preserve the draft through choices. |
| Route a quick question to a cheap side worker | Uses the question and a few relevant paths, and keeps the steer available. | Use the existing worker priority and role/privacy checks. Make this user initiated, pass a bounded brief, and offer a read-only result in Factory. Avoid paying for a follow-up steer wake solely to relay the answer. |
| Keep tool/MCP definitions, order and system instructions stable | Preserves the reusable prompt prefix between turns. | Keep the `agent.open.before` contribution deterministic. Keep volatile state in the Factory UI or late in the request. Leave deliberate tool changes to a work-package boundary. [Claude cache invalidation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#what-invalidates-the-cache) · [OpenAI tool consistency](https://developers.openai.com/api/docs/guides/prompt-caching#manage-tools-with-append-only-updates) |
| Avoid routine reloads of active sessions | Reduces recovery, cancelled work and potential prefix changes after reopen. | Reuse plugin settings and observers. Schedule unavoidable daemon or agent reloads at a checkpoint boundary. Reopening invokes session hooks again. Treat session IDs and config signatures as evidence instead of assuming that every client or plugin refresh changes the provider cache. [Paseo lifecycle](https://paseo.sh/docs/plugins/hooks#naming-and-timing) |
| Compact before TTL during unfinished work, start fresh at a checkpoint boundary | Warm compaction can preserve more details and shrink future input. Avoid keepalive prompts. [Cleanup policy](cold-context-resume.md#c5-idle-cleanup-plugin-timer) · [Codex measurements](codex-research/findings-compact-vs-fresh.md) |
| Use Claude's 1h API cache when the route exposes it and idle gaps justify it | Keeps a reusable prefix through gaps beyond 5m and within 1h. A 1h write costs more, so measure reuse against write cost. | The Messages API accepts `cache_control.ttl: "1h"`. Use it only on a configurable provider route. Factory and the Paseo plugin contract do not control Claude Code request breakpoints. Detect available retention from real route evidence. [Claude 1h cache](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#1-hour-cache-duration) |

## Product decisions

Decided 2026-11-25: no **Continue in a new tab**. **Refresh** clears the context in place (Claude: native `/clear`); with the setting **Keep chat history** it rewinds instead. Codex has no native clear, so a Codex refresh always rewinds and the UI says so. A new setting **Initialize new steer** offers: send the brief at once, place the brief in the Paseo composer to go out with the next prompt, or leave the composer empty and initialize from the steer menu. Questions 2 and the upstream proposal are still open.

1. Should **Refresh this tab** ship with settings changes, or should the first version offer only a new tab for a shorter recovery path?
2. Should Maximum efficiency expose a single confirmed in-place override after an upstream guard lands, or always require a fresh route for affected warm steers?
3. When a replacement brief is ready, should the first version stage it until the next user prompt, or deliver it immediately on the confirmed transition?
